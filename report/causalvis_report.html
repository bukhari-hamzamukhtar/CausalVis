CausalVis, explained from the ground up

A small physics "world model" that watches a video of colliding objects, removes one object in its imagination, replays the scene, and answers "what would happen then?" This report explains every part in plain English: what it does, why we built it that way, what else we could have done, how each version scored, where it still fails, and how it compares with the best published research.

The short answers

You asked many questions. Here are the answers first. Every one is explained in detail further down.

What did we make?
A system that answers "if object X were removed, which collisions would happen?" A language model reads the question, a physics world model re-plays the video without that object, the replay is saved, and the answers are read from the saved replay.
Final score
88.1% of answer options and 66.6% of whole questions correct, on 930 test questions we never used for any tuning. The previous best version scored 74.8% and 30.9%.
Do we beat the top papers?
Partly. We beat NS-DR (the method from the CLEVRER paper itself) by +14.0 / +24.4 points and DCL by +7.7 / +20.1. We do not beat ALOE, VRDP or CRCG; the best of them (CRCG with VRDP) is 8.0 / 21.2 points ahead. And our test questions are not the official test set, so this is an approximate comparison, not an official one.
Did the world model make all the decisions itself?
No. The world model decides how every object moves and bounces. Rules we wrote decide when an object starts being simulated and whether two objects "collided". The language model decides which object is removed and reads the answers. The top neuro-symbolic papers (NS-DR, DCL, VRDP, CRCG) are built the same way: their final answer comes from a separate program, not from the world model. Only ALOE decides everything inside one network, and it has no real physics simulation inside.
Is our key idea new?
No, and we should say so. The idea that gave the biggest jump (use the real video for each object until the removed object could affect it, then simulate) was published in 2024 by the CRCG paper ("Think before You Simulate"). We reached it on our own, but it is not ours alone.
Can the world model decide things itself, or even "talk"?
Yes, it is possible. Four realistic ways, and one idea we did not find anywhere, are listed at the end.

Words used in this report

These words appear again and again. Each is explained once here, in simple terms, and again near where it is used.

World model
A program that has learned how the world moves, so it can predict what happens next. Ours only knows how objects on a table push, slide and bounce.
Simulation / rollout
Letting the world model predict the scene frame after frame, using its own previous prediction as the next starting point.
Counterfactual
"What would have happened if…" A world that did not happen, for example the same video but with one object removed.
Intervention
The change we make to create the counterfactual world. Here: deleting one object.
Frame
One picture of the video. A CLEVRER video has 128 frames (numbered 0 to 127), about 5 seconds.
Trajectory / track
The list of an object's positions over all frames.
Option vs question accuracy
Each question has several options (e.g. "the cube and the sphere collide"). Option accuracy counts options right. Question accuracy only counts a question right if every option is right, so it is much harder.
Train / validation / test
Three separate piles of data. We learn from train, choose settings using validation, and report the final score on test exactly once, so the score is honest.
Momentum
Mass times velocity. In a collision between two objects, the total momentum stays the same: what one loses, the other gains.
Potential energy V
Stored "push" between two objects that depends on how far apart they are. The force is the slope of this energy: steep energy means a strong push.
Friction / drag
The table slowly slows objects down. We measured 0.85% speed loss per frame in CLEVRER.
Impulse
A sudden push delivered at the instant of a collision.
Restitution
How bouncy a collision is. 1 means a perfect bounce, 0 means objects stick. Metal 0.8, rubber 0.5 here.
Voxel
A tiny 3D box, like a 3D pixel. We divide space into boxes 0.02 units wide and record which boxes each object fills.
Normal (contact normal)
The direction pointing straight out of a surface at the point where two objects touch. A bounce pushes along it.
Language model (LM / LLM)
A text AI like ChatGPT. We use a free one on Groq (gpt-oss-120b). A VLM is the same but can also see pictures; ours only reads text.
Neuro-symbolic
A system made of learned parts (neural networks) plus hand-written logic (symbols, programs). Most top CLEVRER methods are this kind.
Program executor
Hand-written code that runs a small "program" made from the question (like: find the cube, remove it, check collisions) to produce the answer.
Calibration
Adjusting a measurement so it matches reality. Our objects came out about 20% too small, so the collision test uses 1.2× their size.
Baseline
A simple method used as a reference point, to show how much the clever parts actually add.
z-score / McNemar test
A number that says how sure we are a difference is real and not luck. Above about 2 means "real". Ours are 10 to 15.
Latent space
The hidden numbers inside a neural network while it works, which normally nobody can read directly.

Module by module: what, how, why, and what else we could have done

For every part we say what it does, how it works, why we built it that way, and a table of the other choices we had and why we did not take them. "Tried" means we built it and measured it. "Not tried" means we decided from reasons or limits, and we say which.

1. The videos and object masks

the recording

What it does. Gives us the raw material: CLEVRER's 20,000 short videos (made with a physics simulator called Bullet) and, for every frame, an outline ("mask") of each object with its colour, material and shape.

How. We use the object proposals that the CLEVRER authors released. They were made by a detector network (Mask R-CNN) that finds objects in each frame. We decode the outlines ourselves in plain numpy.

Why. Training our own detector needs a graphics card (GPU) and we have none. The released proposals are detector outputs, not the hidden true answers, so using them is fair, and earlier methods like NS-DR used them too.

Other optionWhat it would doWhy we didn't
Train our own detectorFind objects ourselves from pixelsNot tried. Needs a GPU; zero budget; the released one is already good on this synthetic data.
Learn straight from pixels, end to endOne big network watches the video and answersNot tried. Needs huge compute and hides the physics inside the network, so nothing could be checked (ALOE does this, see later).
Use CLEVRER's true object positionsPerfect positions for freeNot used at test time. That would be using the answer sheet; the score would not mean anything.

2. Finding the camera and lifting objects into 3D

our fitting code

What it does. Turns flat outlines in the picture into real 3D positions on the table, in the same units for every video.

How. CLEVRER is synthetic: only 3 shapes, one size, and a flat table. So instead of guessing depth, we "invert the renderer": we place a known 3D shape on the table, draw what its outline would look like through the camera, and move it until that outline matches the mask. We first did the same for the camera itself. A cube can also be turned (its "yaw"); since a cube only changes its turning at a collision, we fit its turn as straight lines between collisions.

Why. It is exact for this world and needs no training. Measured: outlines overlap 0.95 with the recovered camera; turn jitter fell from 4.4° to 0.0°.

Other optionWhat it would doWhy we didn't
Use CLEVR's published cameraTake the camera numbers from the older CLEVR datasetTried. It is not CLEVRER's camera: outline overlap only 0.57, and 3D came out worse than 2D.
Depth-guessing network (e.g. MiDaS)Predict how far each pixel isNot tried. Needs a GPU, gives approximate depth, while exact fitting is possible here.
Stay in 2D pixelsSkip 3D completelyTried. 68.0% vs 74.2% with 3D (a real difference, z = 5.5).
Measure cube turn per frameFit each frame on its ownTried. Too noisy (4.4° typical, 16.5° bad cases).

3. Object tracks

the recording our code

What it does. For each object and each of the 128 frames: position, velocity, whether it is on the table, its size, colour, material and shape.

How. Velocity is the average movement over 3 frames. An object's identity is its colour plus material plus shape. When two detections could be confused, we refuse to guess and drop the detection.

Why. We measured that 21% of videos contain two objects with the same colour and shape that differ only in material (for example a blue rubber sphere and a blue metal sphere). Matching by colour alone would silently swap them.

Other optionWhat it would doWhy we didn't
Match objects by colour onlySimpler matchingMeasured wrong in 21% of videos.
Let the model learn object sizeSize as a learned numberTried. Training shrank every object by exactly 30% as a shortcut. Size is now measured, never learned.
Smoothing tracker (Kalman filter)Smoother positionsNot tried. The synthetic video is clean; 3-frame averaging was enough.

4. The world model: one learned energy

the world model

What it does. Knows how objects push each other.

How. It learns only one thing: an energy V between two objects, which depends on the gap between their surfaces and on what they are made of. The push (force) is the slope of that energy, computed by calculus automatically. A small network reads each object's material and shape; mass starts from a sensible guess (metal 1.5, rubber 1.0) and may be adjusted a little. In total the model has 51,909 learned numbers, tiny by today's standards.

Why. Because both objects share one energy, the push on A is always exactly the opposite of the push on B. So momentum is conserved by the maths itself (measured drift 0.00000016 over 500 steps), not because the model happened to learn it. That makes the physics trustworthy and checkable.

WORD · Graph neural network (GNN). A network that looks at objects and their pairs, and passes messages between them. NS-DR's "PropNet" is one. It can learn anything, including physics that breaks the rules.
Other optionWhat it would doWhy we didn't
General network that predicts the next position (GNN)Learn motion freely, like NS-DR and DCLNot our choice. No guarantee of conservation, so small errors add up; our structure forbids a whole class of mistakes.
A real physics engine with a few fitted numbersWhat VRDP does: copy the exact physics law, fit mass and frictionNot our choice. Very accurate on CLEVRER, but only because you already know the exact law of that world. We wanted the model to learn the interaction itself.
Cube orientation and turning forcesLet cubes rotate and push cornersTried. Training blew up (loss jumped from 0.0003 to 5.8); score fell to 71.5%. Corners are not smooth, and the energy needs smoothness.

5. Moving one frame forward, with friction

the world model

What it does. Advances every simulated object by one frame.

How. A "leapfrog" step: half a push, move, half a push. Around it, half a step of friction on each side. Friction is learned per material. Momentum lost to friction is written down as "given to the table".

Why. Leapfrog stays stable over long runs, where the simplest method (Euler) slowly gains or loses energy. Friction was needed because CLEVRER objects really slow down (0.85% per frame), which a pure energy model cannot express. Adding it cut 40-frame prediction error by 25%. The model also found by itself that spheres slow down least, which is right, because they roll.

Other optionWhat it would doWhy we didn't
Simple Euler stepPosition += speed each frameNot our choice. Known to drift in energy over long runs.
No frictionPure energy modelTried. Objects never slow; 25% more prediction error at 40 frames.
One fixed friction numberSame slowing for everythingSuperseded. The model starts from the measured 0.85% and learns how each material differs.

6. Voxel contact and the bounce

the world model's contact step

What it does. When two objects touch, finds exactly where and in which direction, and applies the bounce.

How. Your idea. Space is divided into tiny boxes (voxels) 0.02 units wide. Each object marks the boxes of its surface. Where two objects' boxes meet is the contact point. The direction (normal) is read from the shape of the touching patch: we find the direction in which that patch is thinnest, which for a flat face is straight out of the face. The speed is split into the part along the normal (exchanged, like a textbook bounce) and the part across it (kept). The bounce uses the school formula with bounciness 0.8 for metal and 0.5 for rubber.

Why. A ball hitting a flat face must bounce straight back, wherever it hits. The old method (the line between the two centres) was wrong by up to 34° there. To make it fast, we keep only surface boxes and store each object's box pattern once, then just shift it: 77 ms down to about 4 ms per check.

Line between centresBounce along the centre-to-centre lineTried. Exact for spheres, up to 34° wrong on faces. Bounce error 21.0°.
Snap to the nearest cube faceUse the face directionTried. Worse near edges: 26.8° vs 21.4°.
Exact geometry (GJK/EPA, as in game engines)Mathematically exact closest pointsNot tried. More work; voxels follow your design and work for any shape.

7. How the world model learned

learns from motion only

What it does. Adjusts the 51,909 numbers so predictions match real motion.

How. Take a real moment from a training video, let the model run 20 frames by itself (starting with 3 and slowly growing to 20), measure the distance between predicted and real paths, adjust, repeat. The best version on validation is kept. The last step (v6) ran voxel bounces inside every training step; the bounce direction is fixed geometry, only its strength passes learning signals back. It never sees a single question or answer.

Why. Learning from motion keeps the model general: it learns physics, not the quiz. Keeping the bounce direction fixed stops the model from "cheating" by bending contact directions to lower its error.

Other optionWhat it would doWhy we didn't
Extra weight on contact framesPay more attention to collisionsTried (v3.3, bundled with other changes). Worse on every measure.
Train on questions and answersTune the model to the quiz, like ALOE and VRDP's concept partNot our choice. Needs GPU, and the score would no longer show whether the physics is right.
Let the model learn the bounce directionMore freedomNot our choice. It could learn to point contacts wherever the error is lowest instead of where the surfaces are.

8. Building the "what if" world

our rule world model positions recording

What it does. This is the heart of the system and the change that moved the score from 74.8% to 88.1%. It removes one object and replays the whole scene once.

How. Every object is in one of three states: not here yet, following the real video, or simulated. Objects appear when they appear in the video. An object follows its real motion until the removal can reach it:

  • Lost contact: in the video it was about to touch something that no longer behaves the same (the removed object, or any object already being simulated). It is simulated from 12 frames before that touch.
  • New contact: a simulated object comes close to it.
  • Video ended: after frame 127, everything is simulated for 30 more frames, because CLEVRER also counts collisions just after the video ends.

Why. Before the removal's effect arrives, an object's "what if" path is its real path. Simulating it anyway only adds error. This is causality, not a shortcut, and no collision answers are read. The past-the-end extension was confirmed first: 87% of the missed pairs collide when simulated past the end (typically 14 frames), against 17% of pairs that truly don't collide.

9. Deciding whether two objects collided

rule we wrote, tuned on validation

What it does. Reads the replayed world and writes down every collision with its frame.

How. A collision is counted when the gap between the surfaces drops below 0.03 while the objects move closer, using object sizes multiplied by 1.2. It is not counted again until they separate. The voxel-sensor reading is saved too.

Why. Our 3D objects come out about 20% too small, because the masks' edges are slightly cut off. The ×1.2 calibration was measured on validation against CLEVRER's collision list: detection of real collisions rose from 79% to 98%.

Measured sizes, gap under 0.02No calibrationTried. 84.6% on validation vs 89.0%.

Voxel sensor: sharing a boxStrict touchingTried. 66.1%: our objects rarely share boxes even when they really collided.

10. The stored future

our code

What it does. Saves the whole replayed world: every position of every object in every frame, which objects were simulated from when and why, and every collision.

How. Three forms of one world: a summary file, a full frame-by-frame file (used to draw the 3D GIF), and a plain-text version for the language model.

Why. You asked for the predicted future to be kept in full detail. It also means every answer can be traced back to a line, and all options of one question come from the same world, so they can never contradict each other.

11. The language model

the language model

What it does. Two jobs: read the question and name the removed object; read the stored world and answer each option, quoting the lines it used.

How. Groq's free service with the openai/gpt-oss-120b model (Groq retired the Llama 3.3 model we first used, so the code picks an available model). Answers follow two steps: does the collision happen in the store, then flip it if the question says "will NOT happen". That second step fixed a real bug where it flipped every answer on such questions.

Why. Free, no training needed, and it reads any wording. On 60 test questions it named the right object 60 times out of 60 and scored 86.2%, the same as a plain lookup of the store.

HONEST NOTE. The headline 88.1% (all 930 questions) identifies objects using CLEVRER's question programs, not the language model, because running 930 questions through a free service is slow. The language model matched those programs on 60 of 60 questions we checked. NS-DR, DCL and VRDP use their own trained parsers.

13. Keeping the score honest

the method

What it does. Makes sure the number means something.

How. Physics is learned on the training videos, every setting (detector, sizes ×1.2, +30 frames) is chosen on validation, and test is scored exactly once. We always compare with a simple baseline and check that differences are not luck.

Why. We nearly fooled ourselves once: a version looked better on validation only because it had been picked as the best of 30 tries on validation. On test it was worse.

Why physics improvements barely moved the score for so long

The questions only ask "did these two touch?" A yes/no answer does not change unless a prediction was sitting right at the edge. Making paths 25% more accurate or bounces 9° more correct rarely flips a yes into a no. Worse, the old evaluator often looked at the wrong frames (before the collision, or before an object entered, or not past the end of the video), so no physics could fix those. A full diagnosis of all 3,328 options showed that 610 of 799 missed collisions came from that logic, not from physics.

The hard parts of getting here

  • A wrong diagnosis lasted three weeks. Everyone believed the training only looked one frame ahead. Nobody opened the training loop; it already looked 20 frames ahead. The fix that was planned would have fixed nothing.
  • The model cheated. Allowed to learn object size, it shrank every object by exactly 30%, because that made collisions rarer and the average error smaller.
  • Three changes in one experiment. It got worse and we could not tell which change caused it. Since then: one change per experiment, always with a control run.
  • We almost reported a fake win. A version looked better on validation only because it was the best of 30 tries there. On test it was worse.
  • The camera everyone uses was wrong for this dataset. Our first 3D attempt was worse than 2D until we recovered the real camera.
  • Cube turning broke training, because corners are sharp and the energy needs smooth shapes.
  • A switch that did nothing. The voxel option printed "voxel mode" but that code never ran in the path being scored. Only a digit-for-digit identical score gave it away.
  • The first voxel normal was backwards when objects overlapped a little, which is exactly what happens at real collisions.
  • CLEVRER counts collisions after the video ends. This is not stated for counterfactual questions; we found it only by measuring why 167 pairs were missed.
  • The language model flipped "will NOT happen" answers until its instructions were split into two steps.
  • Limits: one laptop CPU (a single training run took 8 hours), no GPU, zero budget, a free AI model that got retired mid-project, and a Windows shell that silently broke scripts containing backslashes.

So, do we beat the top papers?

We beat two, not the best.

Ahead of NS-DR (the method from the CLEVRER paper itself) by 14.0 points on options and 24.4 on whole questions, and ahead of DCL by 7.7 and 20.1. Behind VRDP, ALOE and CRCG. The closest one, VRDP without extra labels, is 1.8 points ahead on options but 9.1 ahead on whole questions. The best, CRCG on VRDP, is 8.0 and 21.2 points ahead.

Why we are ahead of NS-DR and DCL

  • We use the real video for as long as it is still true. Each object follows its recorded motion until the removal can reach it. Simulating it anyway only adds error. The CRCG paper showed the same idea lifts NS-DR itself from 74.1% to 90.7%, so this is clearly the biggest reason.
  • We simulate past the end of the video, which CLEVRER's answers count.
  • Physics with guarantees: energy-based pushes that conserve momentum, learned friction, and correct 3D contact distances.
  • One consistent world per question, so the options can never contradict each other.

Why VRDP, ALOE and CRCG are still ahead

  • VRDP's physics is an exact copy of CLEVRER's law. It fits a few numbers inside a real physics engine, so long chains of bounces barely drift. Our learned model drifts, which is where most of our remaining errors are (158 missed collisions between simulated objects).
  • They learn from question-answer pairs. ALOE is trained directly on the answers, and VRDP's concept part learns from them too. Our world model never saw a question.
  • CRCG = VRDP's accurate engine plus the "use the video until affected" idea. It combines both strengths.
  • Our reconstructed objects are about 20% too small, which costs collisions until corrected.

How ours is different from the others

  • The world model learns only from motion, never from questions or answers. The score is a test of physics plus logic, not of learning the quiz.
  • Momentum conservation is guaranteed by the model's structure, and friction is written down as momentum given to the table, so the physics can be audited like accounts.
  • Tiny and free: 51,909 learned numbers, trained on a laptop CPU, with a free language model. Top methods use GPUs and much larger networks.
  • Voxel contact points: each collision has a real 3D contact point and direction, not just two centres.
  • A general language model instead of a trained parser, so questions do not have to follow CLEVRER's exact wording.
  • Every answer points to a line in the stored world (for example "frame 65: gray sphere hits cyan cube"), and the whole predicted future can be watched as a 3D GIF.
  • Who gets simulated is decided by reading the simulation as it runs, not by a separate logic program as in CRCG.

What gave us good counterfactual answers, and could others do it?

Three things: using the real video until the removal reaches an object, simulating past the end, and correcting object size for the collision check. None of these is something others could not do. CRCG already published the first one in 2024, and VRDP's engine simulates the full length anyway. What is ours is getting a good score with a small learned physics model that was never trained on answers, running on a laptop at zero cost.

Who actually makes the decisions?

Our world model: no, not all of them.

The world model decides how every simulated object moves, slows down and bounces. The other decisions are made by rules we wrote (when an object starts being simulated, what counts as a collision) and by the language model (which object is removed, the final reading). The top neuro-symbolic papers are built the same way. Only ALOE puts every decision inside one network.

What this means for "are we better than the top leagues?" NS-DR, DCL, VRDP and CRCG also let a separate program make the final decision, with a trained parser reading the question. Our language model plays the role of their parser, and our collision rule plus lookup plays the role of their program executor. So we are compared inside the same family. ALOE is the only one whose network decides everything, but it has no physics simulator you could inspect, and it learned from the answers.

Can the world model decide things itself, or even talk?

Yes, it is possible.

First, one surprise: our world model has very little hidden "latent space". Its thoughts are mostly already readable, because its state is positions, speeds and energy. So "going inside" is easier for us than for a big network. Here are the realistic ways, from easiest to hardest.

  1. Let its own bounce be the decision. When surfaces meet, the model already applies a bounce (an impulse). "A collision happened" could simply mean "the model applied a bounce", which removes our hand-written collision rule. It works once object sizes are corrected.
  2. Twin worlds. Run the real world and the "what if" world side by side with the same model. Any object whose two predicted paths start to separate is "affected". The model itself then decides who must be simulated, replacing our rule. This comes from a classic idea for counterfactuals called twin networks (Balke and Pearl, 1994).
  3. Look inside with small readers ("probes"). Train tiny readers on the model's hidden numbers to answer "will these two collide soon?" A famous study (Othello-GPT) found a hidden game board inside a network this way, and could even edit it to change what the network did. Our model has only a few hidden numbers (64 per object and a 128-number layer in the energy network), so it is easy to probe. For big networks, a newer tool called sparse autoencoders splits the hidden numbers into understandable pieces.
  4. Make it talk through an adapter. Turn the world model's state into word-like vectors that a language model can read, and train on question-answer pairs, as PaLM-E did with robot sensor states. Then the language model reads the world model directly instead of a text file. It needs a GPU for training, though free Colab could handle a small language model.
  5. An idea we did not find anywhere: an "energy diary". The model writes one sentence every time momentum or energy passes between two objects, or to the table. Momentum must always balance, like a bank account, so a wrong sentence would break the balance. That gives a built-in lie detector for explanations. We did not find this in our search, but that does not prove nobody has done it.
